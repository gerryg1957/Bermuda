MoyoDB progress report — 12 August 2026
Project position

MoyoDB has moved from being primarily a database/import/indexing project to having the core of a genuinely useful interactive professional Go pattern-search application.

The clean combined GoGoD/go4go database contains 168,844 canonical games and the position index contains about 35.8 million positions. The database construction, canonical deduplication, source handling and position indexing are working on the full corpus rather than merely on test data.

The Qt application can now load games from the database and external SGFs, replay them on the board, select an arbitrary rectangular area, search the complete professional corpus for that position under board symmetries, and present matching games with their continuations.

What has been established

The pattern-search machinery now supports rotations, reflections and colour reversal; exact regional patterns; an Any wildcard cell; and an optional maximum match move. The existing continuation machinery correctly carries transformations through to the displayed continuation.

The external-SGF workflow is substantially better. An uploaded SGF now displays its actual players using (B) and (W) notation and its komi, rather than presenting the filename as though it were a player. That is enough metadata for the purpose and the display is now satisfactory.

Most importantly, actual Go use has begun validating the purpose of the program. With a large rectangle around an early fuseki position, MoyoDB found only two very close professional precedents. In both, the professionals immediately played the symmetry-equivalent invasion that was under investigation. That is exactly the kind of evidence the project was intended to uncover: not simply “find similar pictures”, but find very close professional precedents and see what the professionals regarded as urgent next.

Performance

There has been a major practical breakthrough here.

The first GUI searches were being run through a debug build and took roughly 140 seconds over the full 168,844-game database. Simply using the release build reduced this to about five seconds.

We then profiled the real application with Linux perf, rather than continuing to guess. That showed that file I/O is negligible; reading the individual move files accounts for only a fraction of one percent of CPU time. The cost lies primarily in pattern matching and Go-board replay.

Two structural optimisations have proved worthwhile:

pattern transformations are now constructed once for a whole database search rather than once for every game;
pattern searching replays a single live board instead of creating a complete vector of cloned PositionStates and calculating SHA-256 position fingerprints that the pattern matcher never uses.

The second change successfully removed the fingerprint/SHA work from the profile. Together the changes produced a modest additional performance improvement and, more importantly, simplified the search path by removing unnecessary work.

A subsequent adaptive row-matching experiment did not improve performance and appears to have made the representative search slower. That experiment should therefore not become part of the retained implementation.

The current useful target is consequently around 4–5 seconds for a full 168,844-game professional database scan on the present machine. That is already comfortably interactive for serious analysis.

Current assessment

The project now feels close to a first coherent result because all the essential pieces finally meet in the GUI:

load a position → select what matters → search the professional corpus → inspect the precedents → examine what professionals played next.

That is materially different from having a collection of backend capabilities. It is now a usable Go-study workflow.

Suggested workplan

I would resist adding large new features immediately. The shortest route to a solid first version is now consolidation.

1. Freeze and preserve today's working state. Confirm that the failed adaptive experiment is absent, run the complete Rust checks, inspect the diff, commit the successful pattern-search/GUI work as a coherent checkpoint, and push it to GitHub.

2. Make release operation normal. Since the debug/release difference is enormous, document that practical GUI use should use a release build. We may eventually make launching it easier, but there is no need to solve packaging yet.

3. Exercise the current search interactively. Try a representative set of real Go questions: whole-corner joseki, large fuseki regions, side patterns, positions with several matches, positions with very few matches, rotations/reflections, and positions from external SGFs. At this stage real use is likely to expose more valuable issues than additional speculative engineering.

4. Polish search-result interpretation. Concentrate on anything that makes the professional evidence easier to understand: first occurrence, continuation, transformation/orientation and moving naturally between matching games. Avoid adding statistics simply because they are possible; add them when actual use shows they answer a question.

5. Establish a small reproducible performance benchmark. The profiler has done its job. Rather than timing videos indefinitely, create one or two fixed pattern searches that can be run from the CLI or a test harness. Then future optimisation can be measured reliably. There is no immediate need to chase sub-second performance: 4–5 seconds over 168,844 games is already useful.

6. Stabilise a first usable release. Once ordinary use stops exposing functional problems, review the documentation, remove experimental CLI options that we decide are not useful, ensure the database/index versioning is sound, and mark a first meaningful MoyoDB version.

7. Only then expand the ambition. The obvious later directions remain richer statistical continuation analysis and a separate corpus of personal games, eventually allowing recurring mistakes to be compared against professional continuations and perhaps analysed with KataGo. Those are compelling next-stage features, but the professional pattern-search application deserves to become a finished thing first.
