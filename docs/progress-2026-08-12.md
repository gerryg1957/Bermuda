MoyoDB progress report — 12 August 2026
Project position

MoyoDB has moved from being primarily a database/import/indexing project to having the core of a genuinely useful interactive professional Go pattern-search application.

The clean combined GoGoD/go4go database contains 168,844 canonical games and the position index contains about 35.8 million positions. The database construction, canonical deduplication, source handling and position indexing are working on the full corpus rather than merely on test data.

The Qt application can now load games from the database and external SGFs, replay them on the board, select an arbitrary rectangular area, search the complete professional corpus for that position under board symmetries, and present matching games with their continuations.

What has been established

The pattern-search machinery now supports rotations, reflections and colour reversal; exact regional patterns; an Any wildcard cell; and an optional maximum match move. The existing continuation machinery correctly carries transformations through to the displayed continuation.

The external-SGF workflow is substantially better. An uploaded SGF now displays its actual players using (B) and (W) notation and its komi, rather than presenting the filename as though it were a player. That is enough metadata for the purpose and the display is now satisfactory.

Most importantly, actual Go use has begun validating the purpose of the program. With a large rectangle around an early fuseki position, MoyoDB found only two very close professional precedents. In both, the professionals immediately played the symmetry-equivalent invasion that was under investigation. That is exactly the kind of evidence the project was intended to uncover: not simply “find similar pictures”, but find very close professional precedents and see what the professionals regarded as urgent next.

Performance

There has been a major practical breakthrough here.

The first GUI searches were being run through a debug build and took roughly 140 seconds over the full 168,844-game database. Simply using the release build reduced this to about five seconds.

We then profiled the real application with Linux perf, rather than continuing to guess. That showed that file I/O is negligible; reading the individual move files accounts for only a fraction of one percent of CPU time. The cost lies primarily in pattern matching and Go-board replay.

Two structural optimisations have proved worthwhile:

pattern transformations are now constructed once for a whole database search rather than once for every game;
pattern searching replays a single live board instead of creating a complete vector of cloned PositionStates and calculating SHA-256 position fingerprints that the pattern matcher never uses.

The second change successfully removed the fingerprint/SHA work from the profile. Together the changes produced a modest additional performance improvement and, more importantly, simplified the search path by removing unnecessary work.

A subsequent adaptive row-matching experiment did not improve performance and appears to have made the representative search slower. That experiment should therefore not become part of the retained implementation.

The current useful target is consequently around 4–5 seconds for a full 168,844-game professional database scan on the present machine. That is already comfortably interactive for serious analysis.

Current assessment

The project now feels close to a first coherent result because all the essential pieces finally meet in the GUI:

load a position → select what matters → search the professional corpus → inspect the precedents → examine what professionals played next.

That is materially different from having a collection of backend capabilities. It is now a usable Go-study workflow.

Suggested workplan

I would resist adding large new features immediately. The shortest route to a solid first version is now consolidation.

1. Freeze and preserve today's working state. Confirm that the failed adaptive experiment is absent, run the complete Rust checks, inspect the diff, commit the successful pattern-search/GUI work as a coherent checkpoint, and push it to GitHub.

2. Make release operation normal. Since the debug/release difference is enormous, document that practical GUI use should use a release build. We may eventually make launching it easier, but there is no need to solve packaging yet.

3. Exercise the current search interactively. Try a representative set of real Go questions: whole-corner joseki, large fuseki regions, side patterns, positions with several matches, positions with very few matches, rotations/reflections, and positions from external SGFs. At this stage real use is likely to expose more valuable issues than additional speculative engineering.

4. Polish search-result interpretation. Concentrate on anything that makes the professional evidence easier to understand: first occurrence, continuation, transformation/orientation and moving naturally between matching games. Avoid adding statistics simply because they are possible; add them when actual use shows they answer a question.

5. Establish a small reproducible performance benchmark. The profiler has done its job. Rather than timing videos indefinitely, create one or two fixed pattern searches that can be run from the CLI or a test harness. Then future optimisation can be measured reliably. There is no immediate need to chase sub-second performance: 4–5 seconds over 168,844 games is already useful.

6. Stabilise a first usable release. Once ordinary use stops exposing functional problems, review the documentation, remove experimental CLI options that we decide are not useful, ensure the database/index versioning is sound, and mark a first meaningful MoyoDB version.

7. Only then expand the ambition. The obvious later directions remain richer statistical continuation analysis and a separate corpus of personal games, eventually allowing recurring mistakes to be compared against professional continuations and perhaps analysed with KataGo. Those are compelling next-stage features, but the professional pattern-search application deserves to become a finished thing first.
## Influence-map development — 13 August 2026

A first interactive influence-map prototype was added to the Qt board.

The initial implementation treated stones as sources of a smoothly decaying
field. Although visually elegant, this proved strategically too naive:
influence passed too readily through opposing stones, dense groups could exert
too much influence simply by containing many stones, and weak or intrusive
stones were not represented convincingly.

Several iterations were tested against a real professional position rather than
against artificial diagrams. This proved especially useful because the errors
could be discussed in Go terms rather than merely as graphical defects.

### Discrete-board principle

An important design conclusion is that the Go board should not be treated as a
low-resolution sampled image.

The meaningful domain consists of the board intersections themselves. There is
no additional information between intersections which should be reconstructed
by interpolation.

A smoothed/interpolated renderer was tested and rejected because it looked
attractive while making strategically meaningful distinctions less clear.

The preferred presentation is therefore discrete and intersection-based.

### Blocked influence propagation

The more convincing model calculates Black and White influence separately.

Own stones act as sources. Influence propagates through empty intersections with
attenuation, while opposing stones block propagation. The strongest surviving
path to an intersection is retained rather than simply summing the influence of
all nearby stones.

The displayed influence tendency is then:

    Black influence - White influence

Values close to zero are deliberately treated as unresolved or neutral rather
than being forced into one colour.

Removing diagonal propagation was tested and made the map less convincing,
particularly across the upper part of the board. Diagonal propagation was
therefore restored.

### Enclosure experiments

Several attempts were made to distinguish territory-like enclosure from ordinary
influence.

A pointwise eight-direction ray model was tried first. It produced arbitrary
one-point gaps, especially near board edges.

A connected-empty-region model was then introduced. Empty regions are
orthogonally flood-filled and their stone boundaries inspected. This produced a
substantial improvement because enclosure became a property of a region rather
than 361 unrelated point judgements.

However, globally connected empty regions can still contain locally secure
pockets. A locally enclosed corner may remain connected through a distant
opening to a much larger mixed region.

A local five-ring enclosure heuristic was therefore tested in addition to the
regional model. Diagnostics showed that this made little practical difference
at important test intersections and was therefore not a sufficient solution.

The current experiment replaces the regional/local enclosure heuristics with an
escape-resistance model. Near-balanced intersections act as candidate open
space. For each colour, the algorithm measures the additional cost of escaping
through that colour's influence compared with ordinary graph distance.

This model has produced the clearest and most strategically interesting map so
far, although important limitations remain.

### Human regression positions

A set of intersections and regions has effectively become a human Go regression
suite for the influence model.

Examples include:

- A19 and the upper-left corner: should read more definitely as Black territory
  than raw influence alone suggests.
- J16 / K16: White's framework should be represented more coherently.
- K2 / L2: highly dependent on who plays first; these should remain unresolved
  rather than being overclaimed by either side.
- M3-P2: White influence has tended to be underrepresented.
- D11: a strategically pivotal point whose value depends strongly on who plays
  first.
- S8 / S10 / S12 / S13 and the upper-right side: a useful test of influence,
  enclosure, move order and tactical constraints.
- the White upper-right framework and candidate invasion/reduction points such
  as O15 and Q14.

These examples are useful precisely because they distinguish different Go
concepts rather than merely asking whether a heatmap looks attractive.

### Emerging conceptual model

The experiments have revealed that several different quantities should not be
collapsed into one number.

**Influence**

Who currently exerts more strategic force at an intersection?

**Enclosure**

How constrained is escape from an area through the opponent's surrounding
structure?

**Leverage / local urgency**

How much would the surrounding position change depending on which colour plays
first at a particular intersection?

This is particularly relevant to positions such as K2/L2 and D11.

The right-side S12/S13 discussion provides an important example. White playing
S12 first can be locally huge, while Black's best defensive option may not be
the corresponding move at the same point. A very bad candidate move such as
Black S13 should not be treated as an equally plausible branch merely because it
occupies the same local area.

Therefore a future leverage model should distinguish:

- one-ply candidate generation;
- best local reply;
- local urgency;
- global move priority.

**Territory / score**

This is a stronger claim and should remain separate from the influence map.
Secure territory depends on life, death, tactical reading and final ownership.
A future score estimator may use some of the same information, but the current
influence display should not pretend to be a score estimator.

### Invasion and reduction insight

A useful human invasion/reduction heuristic was identified.

For example, when considering an invasion of the upper-right White framework,
a player may mentally draw lines between key surrounding stones. Intersections
on the opponent's side of those lines are likely to be too deep, while boundary
points such as O15 and Q14 emerge as candidate invasion or reduction moves.

Rather than hard-coding this rule, a future MoyoDB implementation may be able to
recover similar candidates from the influence/enclosure model by measuring how
strongly hypothetical moves change the surrounding field.

### Proposed next experiment: leverage map

The most promising next development is a one-ply leverage or swing calculation.

For each plausible empty intersection:

1. evaluate the current influence/enclosure map;
2. hypothetically play Black there and recalculate;
3. hypothetically play White there and recalculate;
4. compare the two resulting local maps;
5. rank intersections by how much the local strategic picture changes.

This should identify points which are neutral in ownership terms but highly
important strategically.

A later refinement can examine best replies rather than assuming that both
players should choose the same candidate point.

The immediate goal is not to solve tactics or determine the globally best move.
It is to identify intersections with unusually high local strategic leverage.
