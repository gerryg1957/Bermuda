# MoyoDB Status Report — 10 August 2026

## Executive summary

MoyoDB has reached the point where it is a genuinely useful professional Go study application rather than only a database/search prototype.

The core study loop now works coherently:

> **find a position → see professional continuations on the board → select a continuation → see its supporting games → open the relevant occurrence → study what happened next**

The most important change today was architectural as much as performance-related. Pattern search is now parallel, bounded, deterministic, and uses a bit-parallel matcher designed around the 19×19 Go board representation. On the current 168,390-game corpus, the benchmark search that previously took about one minute now completes in approximately 17.1 seconds with 8 Rayon threads and 14.4 seconds with 16 threads.

The GUI has also become calmer and more board-centred. Professional continuations are selectable directly on the goban, repeated selection toggles the supporting-game filter, and the board now remains physically stable while the surrounding search results and metadata change.

This document describes the current architecture and current-best understanding of the product. It is a status report, not an immutable specification.

---

## 1. Current product workflow

The current investigation workflow is:

1. Load a professional game and navigate to a position.
2. Select a rectangular pattern on the board.
3. Search the complete professional corpus.
4. Treat rotations, reflections and colour reversal as equivalent by default.
5. Collapse continuously matching positions into distinct appearances.
6. Present the immediate professional continuations found after those appearances.
7. Show those continuation candidates directly on the board.
8. Select a candidate to filter the result set to supporting games.
9. Open a supporting game at the occurrence that actually produced the selected continuation.
10. Replay the game and investigate what happened afterwards.

The guiding interpretation remains:

> **MoyoDB should help users discover candidate moves and investigate the professional ideas behind them—not turn frequency or game result into a verdict about move quality.**

Frequency is evidence of professional precedent. It is not an evaluation score.

## 3. Storage and indexing architecture

A MoyoDB project consists principally of:

- SQLite metadata/catalogue data;
- compact `.moves` game records;
- temporary/project support directories;
- the exact whole-board position index.

The exact-position index and arbitrary pattern search are deliberately separate mechanisms.

The existing position index is useful for exact whole-board fingerprints. It does **not** accelerate arbitrary rectangular pattern search, because a rectangle can occur at many positions, orientations and colour assignments.

The pattern-search work therefore operates directly over the compact game records.

---

## 4. Pattern-search architecture

### 4.1 Query equivalence

Ordinary pattern searches include:

- rotations;
- reflections;
- colour reversal.

Equivalent transformed patterns are deduplicated before matching.

Transformation and colour-reversal metadata are retained with each match so that displayed occurrences and continuation coordinates can be mapped correctly.

### 4.2 Appearance semantics

A raw match represents a matching board state.

Chronologically consecutive raw matches with the same:

- game;
- board location;
- transformation;
- colour assignment

are collapsed into one **appearance**.

An appearance retains:

- first matching move;
- last matching move;
- duration.

This avoids treating an unchanged local position as a new professional example after every unrelated move elsewhere on the board.

### 4.3 Immediate continuation semantics

For an appearance beginning at position `N`, the immediate continuation is the move immediately after the **first matching position**.

It is not derived from `last_move_number + 1`.

This distinction is important when the exact pattern remains unchanged for several moves.

## 5. New parallel search architecture

The previous full-corpus search architecture mixed substantial serial work with parallel matching.

The current architecture is:

1. SQLite supplies all game IDs and move-file paths with one bulk query.
2. The game list is divided into bounded batches.
3. Rayon workers process games within each batch.
4. Each worker:
   - reads its own `.moves` file;
   - reconstructs/replays the game positions;
   - searches the positions;
   - collapses raw matches into appearances.
5. The coordinator consumes worker results in original game order.
6. Progress, result ordering and continuation statistics therefore remain deterministic.
7. SQLite connections are not shared across Rayon workers.

The current batch-size rule is based on the Rayon thread count, with a sensible minimum, so memory remains bounded rather than loading the entire corpus at once.

This architecture lets file I/O, replay and matching overlap across games while keeping database access and result aggregation simple.

## 6. New bit-parallel pattern matcher

The most important performance improvement is the current horizontal bit-parallel matcher.

### Previous approach

Even after the first row-bit optimisation, each candidate `(left, bottom)` origin was still tested separately.

For an interior 5×7 pattern on a 19×19 board, many horizontal origins had to be checked independently for every:

- board position;
- transformed pattern variant;
- colour assignment.

Profiling showed that more than 90% of CPU time was inside the record pattern-search path.

### Current approach

The board already stores black and white stones as bitsets.

The matcher now uses a `u64` bitset in which each bit represents a possible horizontal pattern origin.

For a given pattern row:

- black-stone constraints eliminate incompatible origins;
- white-stone constraints eliminate incompatible origins;
- empty-point constraints eliminate incompatible origins;
- the surviving-origin bitset is intersected row by row.

Instead of repeatedly asking:

```text
match at x=0?
match at x=1?
match at x=2?
...
```

the matcher progressively eliminates all impossible horizontal placements together:

```text
possible origins: 111111111111111
after constraint: 101001001000101
after next row:   001001001000001
after next row:   000001000000001
```

Each remaining set bit is a complete matching horizontal origin.

Edge constraints also restrict the legal origin range before matching, so patterns explicitly touching or not touching board edges do not waste work on impossible placements.

The matcher remains exact. It changes the computation, not the search semantics.

## 7. Performance status

Current real-corpus benchmark:

- corpus: **168,390 games**
- benchmark pattern: 5×7 interior pattern
- equivalence: rotations + reflections + colour reversal
- 8 Rayon threads: **17.11 s**
- 16 Rayon threads: **14.43 s**
- peak RSS: approximately **200 MB**

Immediately before the horizontal bit-parallel matcher:

- 8 threads: **55.94 s**
- 16 threads: **46.86 s**

An earlier 8-thread full-corpus baseline was approximately **59.22 s**.

The horizontal bit-parallel change reduced 8-thread CPU work from approximately **379 CPU-seconds to 105 CPU-seconds**, demonstrating that the gain is primarily algorithmic rather than merely additional threading.

A small regression benchmark retained the same SHA-256 output checksum after the search-architecture changes, providing a useful correctness check for the tested query.

At this point search performance should be regarded as adequate for normal interactive development. Further profiling may still reveal worthwhile improvements, but performance is no longer the immediate architectural blocker.

## 8. Search-result and continuation architecture

The project search returns bounded summary information rather than eagerly loading every detailed occurrence into the GUI.

The summary report contains:

- matching games;
- appearance counts;
- immediate-continuation distribution;
- supporting game IDs for each normalized continuation.

The GUI keeps the complete unfiltered result rows separately from the currently displayed rows.

Selecting a continuation:

1. transforms the clicked board coordinate back into normalized query coordinates;
2. looks up the supporting game IDs;
3. filters the visible result model;
4. stores the selected normalized continuation.

When a supporting game is subsequently opened, its detailed occurrences are loaded lazily.

The occurrence loader marks which occurrence produced the currently selected continuation, allowing the GUI to open the game at the supporting occurrence rather than simply at occurrence zero.

This gives the user a direct chain from candidate move to actual professional example.

## 9. GUI architecture and current interaction

The goban is becoming the primary interaction surface for professional candidate moves.

### Continuation markers

Professional immediate continuations are drawn directly on the board.

Their current visual semantics are:

- marker position = where the professional move was played;
- marker existence = professional precedent exists;
- marker size = relative frequency;
- outer selection ring = continuation currently being investigated.

Frequency uses square-root scaling so visual area does not exaggerate differences excessively.

The markers use relatively stable opacity rather than stronger colour intensity for more frequent moves. This helps them read as Go-board annotations rather than as a quality heat map.

### Selection behaviour

A continuation marker is clickable.

Selecting it filters the search results to supporting games.

Selecting the already-selected continuation again clears the filter and restores the full search-result set.

The existing frequency-ordered candidate list remains available as supporting information and retains A/B comparison controls, but it is no longer the only or most natural way to select a continuation.

### Stable board geometry

The board frame is now width-driven and square rather than taking arbitrary leftover vertical space.

This prevents the goban from resizing when:

- search results are filtered;
- a different supporting game is selected;
- metadata below the board changes height.

The board therefore acts as the stable visual centre of the investigation.

## 10. Evidence and evaluation remain separate

Several distinctions remain fundamental to the product design.

### Professional frequency

Frequency means that a move occurred more often in the matching professional examples.

It does not mean:

- best move;
- objectively stronger move;
- recommended move.

### Historical results

Game outcome is descriptive context.

It must not silently become evidence that the local continuation caused the eventual game result.

### KataGo

Future KataGo integration should provide exact whole-board engine evidence.

That evidence should remain visibly separate from professional-corpus precedent.

Professional corpus and engine analysis answer different questions:

- **corpus:** what did strong human players actually try in comparable situations?
- **engine:** what does a strong modern evaluator think about this exact whole-board position?

Disagreement between them can itself be educational.

### Influence

A possible future influence display should remain a heuristic concept distinct from KataGo ownership.

Ownership must not silently be relabelled as influence.

## 12. Known issues and deferred work

The following are deliberately not blockers to the current application:

- The blue matched-pattern rectangle is visually prominent; increasing its translucence is a likely later polish change.
- The earlier sparse Chinese-opening “weird occurrence” should still be retained as a specific regression case and investigated rather than explained away.
- A dedicated regression test for an appearance created/removed specifically by capture remains technical debt.
- Very short application-window behaviour should be checked now that the goban width determines its height; the lower information area may eventually need scrolling or another constraint.
- Further pattern-search profiling is possible, but the present 14–17 second full-corpus benchmark has removed performance as the immediate priority.
- Local-activity measurements remain useful experimental evidence but are not currently a user-facing feature.
- A separate corpus of personal games, with later pattern/KataGo analysis of recurring mistakes and habits, remains a possible future direction.

## 13. Suggested next development phase

The best next phase is not another large subsystem.

The application should now be used on real study questions and allowed to reveal where friction remains.

Likely near-term work is therefore:

1. small visual polish, including the matched-pattern overlay;
2. continued refinement of board-first candidate investigation;
3. regression testing around transformed/sparse pattern cases;
4. documentation of architectural invariants and search semantics;
5. only then deciding which larger analytical feature deserves to come next.

The important milestone is that the current application already supports a coherent professional-game investigation loop.

---

## 14. Architectural principles worth preserving

As MoyoDB develops, the following principles have emerged as especially valuable:

- The Rust library is the source of core behaviour; CLI and GUI are clients of it.
- QML presents and controls the application but does not own database logic.
- SQLite access remains controlled and is not casually shared across parallel workers.
- Parallelism must preserve deterministic visible behaviour.
- Pattern equivalence should match how Go players reason about shape, not force irrelevant orientation or colour distinctions.
- Search results are evidence, not verdicts.
- The board is the natural language of Go and should carry the primary spatial interaction.
- Expensive details should be loaded lazily when the user asks for them.
- Historical breadth should be preserved rather than discarded simply because styles change.
- Architectural documents describe the current best understanding and may evolve as the application teaches us more about the problem.
