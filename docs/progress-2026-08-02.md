MoyoDB progress report — 2 August 2026


Purpose

MoyoDB is being developed as a native replacement for MoyoGo Studio: a database of professional Go-games supporting large collections, incremental imports, game replay, exact-position indexing and visual pattern search.

The project is written primarily in Rust. The graphical application uses Qt 6, QML, Kirigami and CXX-Qt.

Current known limitations

Raw occurrence counts. A pattern is currently counted at every game position where it exists. When moves are played elsewhere, an unchanged local pattern can therefore produce many consecutive matches. A future refinement should collapse consecutive matches at the same board location into one “match episode”.

Synchronous searches. The interface displays a searching state, but the core search itself remains synchronous. Very large databases may temporarily block the interface. A later implementation should run searches in a worker thread and support cancellation and real progress reporting.

Distribution and packaging. The application currently builds from source. It does not yet have Flatpak, AppImage, RPM or Debian packaging.

Testing data. A small distributable SGF corpus or ready-made test project is not yet included, making first-time testing less straightforward than it should be.

Cross-platform testing. Development has principally taken place on openSUSE Tumbleweed. GNOME and other desktop environments need documented testing.

Recommended next steps

Test on GNOME under both Wayland and X11/XWayland.
Test search performance on a substantial real database.
Collapse persistent consecutive matches into match episodes.
Move searches to a background worker.
Add filtering, sorting and richer metadata controls.
Consider the planned separate corpus for users’ personal games and recurring-mistake analysis.

## Update — 3 August 2026: Database workflow foundation

### Purpose

This milestone prepares MoyoDB's database-management operations for use
from the Qt GUI without invoking or parsing command-line programs.

The GUI will call stable Rust library APIs directly. Long-running work
will run outside the GUI thread and report structured progress back to
QML.

### Core import operation

Directory import has been refactored into a reusable library operation.

It now provides:

- a discovery stage that counts SGF files before import;
- determinate progress during import;
- the current SGF path;
- counts for imported games, added sources, duplicates, skipped games
  and errors;
- elapsed time and processing rate;
- an import error-log path;
- cancellation between SGF files;
- a final completed or cancelled outcome.

Cancellation does not roll back SGFs already imported. Each completed
file remains safely committed, and the database remains internally
consistent.

The existing command-line `import-dir` operation now uses this shared
library API rather than maintaining a separate implementation.

### Position-index operation

Position-index building has also been moved into a reusable library
operation.

It now provides:

- the active index version;
- the number of games awaiting indexing;
- processed and successfully indexed game counts;
- the number of indexed positions;
- error count and error-log path;
- elapsed time and processing rate;
- cancellation between games;
- completed and cancelled outcomes.

Indexing one game is transactional. A cancelled build therefore leaves
a valid partial index which can be resumed by running the operation
again.

The command-line `build-position-index` command now uses the same
library implementation intended for the GUI.

### Qt background worker

A new QML-facing `DatabaseOperationModel` has been implemented with
CXX-Qt threading support.

It supports three operations:

1. create a database, import an SGF directory and optionally build the
   index;
2. add games to an existing database and optionally update the index;
3. update the position index independently.

The model exposes structured properties for:

- operation and stage names;
- status and error messages;
- the resulting project path;
- current file or game;
- import progress and summary values;
- index progress and summary values;
- elapsed time and rate;
- cancellation state;
- import and index error logs.

Long-running work runs on a background Rust thread. Progress updates are
throttled to approximately ten updates per second so that large imports
and index builds do not overwhelm the Qt event queue.

An atomic cancellation token is shared with the worker. An operation ID
prevents delayed messages from an older operation from updating the
model after a newer operation has begun.

## Update — 3 August 2026: GUI database workflows completed

### Implemented GUI workflow

MoyoDB now provides a top-level **Database** menu with working
operations for:

- creating a new database;
- adding SGF games to the current database;
- building or updating the position index;
- viewing the current operation;
- cancelling the current operation.

The GUI invokes the shared Rust library APIs directly through the
CXX-Qt `DatabaseOperationModel`. It does not run command-line programs
or parse their output.

### Database forms

A shared database-import form supports both creation and addition.

Database creation collects:

- database name;
- parent destination folder;
- SGF source folder;
- source name;
- source version;
- whether to build the position index after import.

Adding games collects:

- SGF source folder;
- source name;
- source version;
- whether to update the position index afterward.

The current database path is shown as read-only when adding games.

### Shared progress and result dialog

One dialog is used for discovery, import, indexing, completion,
cancellation and failure.

It displays:

- operation and stage;
- indeterminate progress during discovery;
- determinate import and index progress;
- processed and total counts;
- imported games;
- added sources;
- duplicates;
- skipped games;
- import errors;
- indexed games and positions;
- index errors;
- current file;
- elapsed time and rate;
- error-log paths;
- cancellation and failure explanations.

Completed dialogs no longer retain an unnecessary empty progress bar.
Zero-work index updates display a clear 0-of-0 summary. Rate units
correctly distinguish SGF import from game indexing.

### Project refresh behaviour

After creating a database, the returned project path becomes the active
GUI project and the catalogue is loaded automatically.

After adding games, the game catalogue refreshes and stale game/search
selection state is cleared.

Cancellation after partial import still opens the valid partial
database and displays its successfully imported games.
